# 开源车牌识别试水实验报告

**实验时间：** 2026-11-03（UTC）夜间；**实验地点：** 本机 CPU（无 GPU）。
**一句话结论：** HyperLPR3 在公开 CCPD 数据上真的跑起来了，绿牌 8 位全牌准确率 **90.0%（270/300）**，且 D/F 位在检出样本中几乎全对；主要短板不是 8 位本身，而是省字（皖→粤的系统性偏见）和 11 张漏检。PaddleOCR 在本机试水窗口内没有跑起来（见第 2 节），没有它的准确率数字，本报告不编造。

> 口径声明：本报告里的每一个准确率都可以从 `results/` 下的 CSV 用 `scripts/evaluate.py` 复算出来；没有一张预测结果是手写的。LLM/多模态大模型没有参与任何一次 OCR。

## 1. 准确率总表（主结果：整图输入，HyperLPR3）

| 样本集 | 样本数 | 检出率 | 全牌准确率 | 单字准确率 | 平均耗时/张（CPU） |
|---|---|---|---|---|---|
| 绿牌 8 位（CCPD2020 test） | 300 | 96.3%（289/300） | **90.0%（270/300）** | 94.6%（2270/2400） | 0.087 秒 |
| 蓝牌 7 位（CCPD2019 ccpd_fn，对照） | 100 | 96.0%（96/100） | **70.0%（70/100）** | 89.4%（626/700） | 0.098 秒 |

**统计口径：** 全牌正确 = 预测字符串与真实牌号全部字符一致（含省字）；单字准确率 = 对齐位置上正确的字符数 / 真实字符总数；未检出计为全牌错误、单字 0 分。

**新能源关键位（第 3 位 D/F）：**
- 按全部 300 张算：286/300 = **95.3%** 正确；
- 按检出的 289 张算：第 3 位正确 286/289 = **99.0%**；
- 也就是说，D/F 本身几乎不是问题，D/F 丢分几乎全部来自 11 张漏检和 3 张位数错（见下）。

**绿牌 30 张错误拆解（300 − 270）：**
- 未检出：11 张
- 位数错（输出 7 位，把 8 位绿牌截成 7 位）：3 张 —— 这正是老系统在新能源牌上的同款失败模式，HyperLPR3 在本样本里也有 3 例，不是零
- 同位数、仅 D/F 错：1 张
- 其他字符错：15 张

**按位置的准确率（仅检出样本）：**
- 绿牌：第 1 位（省字）94.8%（274/289），其余各位 98.3%–99.7%
- 蓝牌：第 1 位（省字）78.1%（75/96），其余各位 92.7%–97.9%
- 省字混淆（绿牌 15 个省字错误中）：皖→粤 10 个，皖→浙/京/苏/豫各 1 个，皖→B 1 个
- 省字“只错省字、其余全对”的情况：绿牌 9/30 个错误，蓝牌 14/30 个错误

**置信度参考（不是阈值结论）：** 绿牌正确样本平均置信度 0.985，错误且检出的样本平均 0.858；蓝牌对应为 0.984 / 0.914。置信度有一定区分力，但两组有重叠，不能只凭一个阈值就自动覆盖。

**蓝牌为什么低，不要直接解读为“蓝牌更难”：** 蓝牌样本来自 CCPD2019 的 ccpd_fn 子集（远/近拍摄难度集），不是 CCPD-Base 通用集，本身就更难；绿牌样本来自 CCPD2020 test 通用集。两者难度口径不同，70% vs 90% 不能直接对比出“绿牌比蓝牌好认”。

### 1.1 补充实验：按真实框裁切后输入（同一批样本，同一模型）

| 样本集 | 全牌准确率 | 单字准确率 | 检出率 |
|---|---|---|---|
| 绿牌裁切 | 88.0%（264/300） | 93.9%（2253/2400） | 95.7%（287/300） |
| 蓝牌裁切 | 61.0%（61/100） | 87.3%（611/700） | 94.0%（94/100） |

**这个补充实验的结论是反直觉的，必须写清原因：** 我用的裁切是“按真实四顶点取轴对齐外接矩形 + 25% 边距”，倾斜车牌会被包进大量背景、长宽比也被拉变形；而 HyperLPR3 整图模式内部会做关键点透视矫正。所以裁切后反而更差，**不能**据此断言“用户的抓拍车牌图效果会更差”——用户的卡口裁切图是相机自己切的、通常是正对的大车牌，和我这种粗糙的外接矩形裁切不是一回事。正确的下一步是用真实卡口裁切图重测，而不是用这个裁切数去否定复检路线。

## 2. 模型：装了什么、跑通了什么、卡在哪里

### 2.1 HyperLPR3 —— 跑通 ✅

- 安装命令：`./venv/bin/pip install hyperlpr3`
- 实际装上：hyperlpr3 **0.1.3**，onnxruntime 1.31.1，opencv-python 5.0.0.93，numpy 2.5.4（后续装 PaddleOCR 时 numpy 被降到 2.3.5，见 2.2）
- 首次 `import` 时自动从模型源拉取约 **11.9MB** 模型到 `~/.hyperlpr3`，无需手动下载权重
- 调用方式：`LicensePlateCatcher()`（默认 ONNX Runtime、detect_level=LOW），输入整图，返回 `[plate_code, rec_confidence, plate_type, det_bound_box]`
- 踩过的坑（已解决，写进脚本里了）：0.1.3 的多任务流水线返回的是列表 `to_result()`，不是 Plate 对象；按对象写法取 `plate_code` 会报 `AttributeError: 'list' object has no attribute 'plate_code'`。`scripts/run_hyperlpr3.py` 已同时兼容列表/字典/对象三种返回形状。
- 速度（本机 4 核 CPU）：绿牌平均 0.087 秒/张，蓝牌 0.098 秒/张。这个速度是“整图检测 + 识别”的 CPU 速度，不是 GPU 速度，也不是 2000 万张/天的压测结论。

### 2.2 PaddleOCR —— 装上了，没跑起来 ❌（只有安装事实，没有准确率）

- 安装命令：`./venv/bin/pip install paddleocr`
- 实际装上：paddleocr **3.7.0**、paddlex 3.7.2；同时把 numpy 从 2.5.4 降到 2.3.5，并装了 opencv-contrib-python 4.10.0.84
- **关键事实：`pip install paddleocr` 并没有装上 paddlepaddle 运行时**（`pip list` 里没有 paddlepaddle），这是后续跑不起来的可能原因之一，但本实验没有验证“补装 paddlepaddle 后就能跑”，所以不写成定论
- 两次首次运行 `PaddleOCR(lang='ch')` 都卡在同一点：PaddleX 下载 `PP-LCNet_x1_0_doc_ori` 模型，6 个文件下到第 5 个（83%）后停滞，`~/.paddlex` 目录始终为空；第二次用 `PADDLE_PDX_DISABLE_MODEL_SOURCE_CHECK=True` 后台重试，同样卡在 83%，且进程随一次服务重启消失
- 结论：PaddleOCR 在本机、本窗口内**未跑通、未测出准确率**。下一步要重试的话，路线是：单独装 paddlepaddle CPU 版 + 在网络更好的环境下预下载 PaddleX 官方模型文件，而不是在本机反复重试同一个下载点。

### 2.3 LPRNet —— 本次未尝试（不是“失败”）

- 原因：需要另装 PyTorch CPU（数百 MB）+ 找可用的中文预训练权重 + 适配代码，超出“先跑通一个模型”的试水范围；HyperLPR3 已经给出完整结果后，没有为凑数而硬上
- 如实记录：LPRNet 的准确率在本报告里是**空白**，不是零分

## 3. 数据集：来源、样本数、抽样方法

### 3.1 绿牌（主样本）

- 来源：Zenodo 存档记录 15647076（CCPD 的存档版，原始仓库 github.com/detectRecog/CCPD）
- 文件：`CCPD2020.zip`，907,711,344 字节，MD5 **eb93e88c5988879f8da6f92bbf083324**（下载后实测，与 Zenodo 标称一致）
- 解包后：`CCPD2020/ccpd_green/`，train 5769 张、val 1001 张、test 5006 张，共 11776 张图（压缩包内共 11781 个条目，含目录）
- 本实验用 **test 集**，按文件名排序后用 seed=42 洗牌，取前 **300 张**
- 标签：全部从文件名按 CCPD 规则解析（省字表、字母表、字母数字表，`O` 为无字符占位符并剔除），解析器见 `scripts/ccpd_parse.py`，并用文档示例 `皖AY339S` 做过断言自检；没有一张标签是人工猜的

### 3.2 蓝牌（对照样本）

- 来源：同一 Zenodo 记录的 `CCPD2019.tar.xz`（13,164,924,944 字节），**没有全量下载**
- 实际做法：用 HTTP Range 只下载前 400,000,001 字节（382 MiB）到 `data/ccpd2019_partial.tar.xz`，再用 tar 解包；因截断 + 属主问题 tar 退出码为 2，但仍解出 **9860 张**，全部位于 `CCPD2019/ccpd_fn/`（远/近难度子集）
- 本实验用这 9860 张，同样 seed=42 洗牌，取前 **100 张**
- 标签：同样从文件名解析；蓝牌为 7 位（省字 + 字母 + 5 位）

### 3.3 数据集本身的局限（必须写在结论前面）

- CCPD 是合肥停车场手持拍摄，车牌在图里很小（示例中约 60×30 像素），且几乎全是皖牌；卡口是近景、正对、大车牌，且用户场景以沪牌为主。**所以本报告的 90% 不能直接当成卡口上线后的准确率**，它只能证明“开源模型能认 8 位绿牌、D/F 位不是瓶颈、省字是主要误差源”这三点。
- 样本量 300 + 100 在 CPU 上是可承受的试水规模，但 90% 的 95% 置信区间大约在 ±3.4 个百分点左右（按二项近似估算，仅作量级参考），不要把 90.0% 读成精确到小数点后一位的工程承诺。

## 5. 下一步建议（按优先级）

1. **最值得微调的是 HyperLPR3，不是 PaddleOCR。** 理由全部来自实测：它已经在本机跑通、CPU 上 0.09 秒/张、绿牌 90% 且 D/F 位检出后 99% 对。PaddleOCR 连跑起来都没做到，现阶段不值得为它再花一个晚上。
2. **先解决省字，再谈整体准确率。** 省字错误占绿牌错误的近一半（15/30 个错误含省字错，其中 9 个只错省字）。可行的方向（均为建议，未在本实验验证）：用自有数据微调省字分类；在卡口场景下利用“本站点主要省份”做先验约束（例如沪牌为主时，省字候选优先沪，但必须保留人工复核出口，不能硬编码成只认沪）。
3. **下一轮必须用真实卡口裁切图重测。** 样本建议：至少绿牌、蓝牌各数千张，覆盖白天/夜间、晴/雨、倾斜、脏污；重点看三项：全牌准确率、D/F 位准确率、省字准确率。CCPD 的 90% 只能当起点，不能当上线指标。
4. **不要把“截断成 7 位”当成已解决。** 本样本里 HyperLPR3 仍有 3 张把 8 位截成 7 位，说明即使换了新模型，也要在复检规则里加一道“绿牌必须 8 位、蓝牌必须 7 位，否则进人工队列”的硬校验，不能只信模型输出。
5. **PaddleOCR / LPRNet 的后续处理：** PaddleOCR 建议在网络更好的机器上先单独装 paddlepaddle CPU + 预下载模型文件，再测 100 张对比；LPRNet 建议只在 HyperLPR3 微调后仍不达标时再引入，作为第二候选，而不是现在平行开三个坑。

## 6. 复现方法与文件清单

**环境：** Python 3.12.3，独立虚拟环境 `venv/`，无 GPU，4 核 CPU，内存 7.7GB。

**复现命令（全景模式）：**

```bash
cd ~/workspace/plate-trial
python3 -m venv venv
./venv/bin/pip install -U pip wheel
./venv/bin/pip install hyperlpr3
./venv/bin/python scripts/run_hyperlpr3.py \
  --green-dir data/CCPD2020/ccpd_green/test --n-green 300 \
  --blue-dir data/ccpd2019_partial/CCPD2019/ccpd_fn --n-blue 100 \
  --seed 42 \
  --out results/hyperlpr3_fullscene_combined.csv
./venv/bin/python scripts/evaluate.py results/hyperlpr3_fullscene_combined.csv
```

| 文件 | 说明 |
